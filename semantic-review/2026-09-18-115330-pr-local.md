# Quality and maintainability review of GymBro

GymBro is a vanilla-JS PWA for tracking gym workouts, exercises, and weight history on top of IndexedDB. The code is genuinely clean for a personal project: a thin `db.js` wrapper, a domain `store.js` that owns all business logic, a tiny hash router, and per-view render functions. The domain model is well factored — workouts contain days, days contain items, items are either `single` or `superset`, and weight history lives in a separate store keyed by `exerciseId`. The main issues are not bugs in the happy path but structural: duplicated file-export and weight-dialog logic across views, two near-identical `mBtn`/`menuBtn` helpers, module-level render caches in `scheda.js` that are fragile under the single-view router, and unhandled edge cases in the data model (dangling `exerciseId` references, unenforced superset arity, no error surface when IndexedDB writes reject).

Watch for: module-level caches in `scheda.js` shared across renders (**confirmed**); `window.setViewTitle`/`window.triggerInstall` globals as the view/shell contract (**confirmed**); duplicated export-download and weight-log dialog code across three views (**confirmed**); dangling `exerciseId` after `deleteExercise` leaves items rendering as "(esercizio)" with no repair path (**confirmed**); `saveWorkout`/`logWeight` rejections are swallowed with no user feedback (**likely**).

**Verdict**: NEEDS_CHANGES

## High-level view

The layering is sound. `db.js` knows only IndexedDB primitives, `store.js` owns every domain rule and is the single place that touches stores, and views never reach into `db` except for the deliberate `store.db.clearAll()` escape hatch in settings. That discipline is worth preserving.

The most valuable refactors are about duplication, not correctness. The blob-download-and-revoke dance is copy-pasted in `schede.js` and `impostazioni.js`, the weight-logging modal is reimplemented in both `scheda.js` (`quickWeight`) and `esercizi.js` (`addWeight`), and two files define a `mBtn`/`menuBtn` action-row button that differ only in trivia. All three belong in `ui.js`.

The shakiest structural choice is the module-level `latestCache`/`nameCache`/`progressCache` in `scheda.js` combined with a router that fully re-renders on every navigation. They work today because they're reset per render, but they are global mutable state keyed by nothing that a future concurrent render or partial update would corrupt silently. The same category of implicit coupling shows up in the `window.setViewTitle` and `window.triggerInstall` globals that form the undocumented contract between the shell and the views.

On the data model, the gaps are around referential integrity and failure surfaces: deleting an exercise leaves workout items pointing at a missing id with no cleanup or warning, superset items with fewer than two exercises are representable but never guarded, and every `await store.save…()` assumes success — an IndexedDB quota or transaction error rejects silently and leaves the UI showing stale state.

Offline behavior is otherwise solid — network-first for app code so updates land, cache-first for static assets, with a controlled skip-waiting handshake. The gaps: a failed network fetch for a non-cached, non-HTML asset rejects with no fallback, and the `isAppCode` check treats every path ending in `/` as app HTML.

1. **Duplicated file download** — the blob/createObjectURL/anchor-click/revoke sequence is copied in `schede.js:exportSingleWorkout` and `impostazioni.js:exportBackup`. Extract a `downloadJSON(filename, data)` helper into `ui.js`.

3. **Duplicated menu-button helper** — `schede.js:menuBtn` and `scheda.js:mBtn` are near-identical action-row buttons that both hand-close the modal via `document.querySelector('.modal-backdrop')`. Move one version to `ui.js`.
4. **Module-level render caches** — `latestCache`/`nameCache`/`progressCache` in `scheda.js` are module globals reset per render; fragile under the re-render-everything router. Scope them to the render call or a per-view state object.
5. **Modal-close by DOM query** — `mBtn`/`menuBtn` close the modal with `document.querySelector('.modal-backdrop')?.remove()` instead of the `close` handle `openModal` returns, so they leak listeners and break if two modals ever stack. Thread the real `close`.
6. **`window.*` shell contract** — `setViewTitle`, `triggerInstall`, `__canInstall` are implicit globals coupling views to `app.js`. Export a small `shell` module instead.
7. **Dangling exerciseId on delete** — `deleteExercise` removes the exercise and its logs but leaves workout items referencing the dead id; they render as "(esercizio)" and their own edit sheet returns early on the null lookup, so the row can only be removed from the day menu. Block/warn when referenced, sweep items on delete, or offer a remove path from the orphaned row.
8. **Silent write failures** — `saveWorkout`, `logWeight`, `importData` etc. never catch rejected IndexedDB transactions; a quota/error leaves the UI stale with no toast. Wrap save paths and surface failures.
9. **Superset arity not guarded** — a `superset` item with 0–1 exercises is representable (e.g. via import) and renders as an empty labeled block. Guard rendering and construction.
10. **Non-atomic import** — `importData` clears all three stores then writes them in separate transactions with no rollback; a mid-import failure leaves a partial DB after the destructive clear. Use a single transaction or a staged import-then-swap.
11. **SW fetch gaps** — non-cached, non-app assets reject with no fallback offline, and `isAppCode` maps any `/`-terminated path to HTML. Add a cache/opaque fallback and tighten the check.

<summary>Details</summary>

### Duplicated export/download plumbing

The "serialize to JSON, wrap in a Blob, create an object URL, click a hidden anchor, revoke after a timeout" sequence appears verbatim in `schede.js:exportSingleWorkout` and `impostazioni.js:exportBackup`. They differ only in the filename and which `store.export*` they call. A `downloadJSON(filename, dataObj)` in `ui.js` collapses both call sites to one line and puts the object-URL lifecycle in a single place (**confirmed**).

The "read a File, `JSON.parse`, dispatch to a store import, toast, navigate" shell is likewise duplicated in `impostazioni.js:importBackup` and `importSingleWorkout`. They diverge on replace-vs-merge, but the file-reading and try/catch wrapper is identical and could share a `readJSONFile(inputEvent)` helper (**confirmed**).

### Duplicated weight-logging dialog

`scheda.js:quickWeight` and `esercizi.js:addWeight` independently build the same modal: a numeric `Peso (kg)` input prefilled from the latest log, a note input, a date input defaulting to `todayISO()`, and a Save that calls `store.logWeight`. `quickWeight` additionally passes `workoutId` and pokes `latestCache`; `addWeight` refreshes via `router.handleRoute()`. The shared body plus two divergent refresh strategies is what drifts — a fix to one (input validation, say) won't reach the other. A single `weightDialog(exerciseId, { workoutId, onSaved })` would centralize it (**confirmed**).

### Two near-identical menu-button helpers

`schede.js` defines `menuBtn(label, onClick, danger)` and `scheda.js` defines `mBtn(label, onClick, danger)`, both rendering a left-aligned block ghost button that closes the current modal and runs the callback. They differ in how the callback receives close (`menuBtn` passes it in, `mBtn` closes first). The `danger` branch in `menuBtn` is a no-op ternary (`'btn-ghost' : 'btn-ghost'`) — both arms are the same class, so danger styling comes only from the inline `color` (**confirmed**).

Both close the modal via `document.querySelector('.modal-backdrop')?.remove()`. `openModal` returns a `{ close }` handle that also tears down the keydown and visualViewport listeners; `.remove()` skips that cleanup and grabs whichever backdrop is first in the DOM — if a confirm dialog is ever opened over a menu, this closes the wrong one (**confirmed**). Threading the real `close` fixes both the listener leak and the stacking hazard.

### Module-level caches under a re-render-everything router

`scheda.js` keeps `latestCache`, `nameCache`, and `progressCache` at module scope. `preloadLatest` clears and repopulates all three at the start of every `renderScheda`, and `rerender()` calls `router.handleRoute()` which re-invokes `renderScheda`, so within a single scheda view they stay consistent. The fragility is structural: these are process-global maps holding data for "the currently rendered workout" with no key tying them to a workout id. Any change that renders two things, or updates a cache outside a full re-render (as `addExercise`/`quickWeight` already do), risks showing one workout's weights under another's exercise. A per-render state object, or caching keyed by workout id, removes the hazard (**confirmed**).

```
renderScheda(w)
  └─ preloadLatest(w)  → resets 3 module globals
       ├─ latestCache[exId]   (also written ad-hoc by addExercise/quickWeight)
       ├─ progressCache[exId]  (only ever written here → stale after quickWeight)
       └─ nameCache[exId]
```

Note the asymmetry: `quickWeight` refreshes `latestCache[exerciseId]` after saving but not `progressCache[exerciseId]`, then calls `rerender()` which re-runs `preloadLatest` and rebuilds everything anyway. The manual `latestCache` write is therefore dead — the subsequent full re-render overwrites it. Harmless, but it signals the cache layer isn't earning its keep; since `rerender` already refetches, the ad-hoc pokes could go (**confirmed**).

### `rerender` scroll-restore fights the router's reset

`rerender()` captures `window.scrollY`, calls `router.handleRoute()`, then restores scroll twice (immediately and in a `requestAnimationFrame`) because `handleRoute` unconditionally resets scroll to top. Every in-place edit rebuilds the entire view DOM and then re-scrolls — a full teardown per weight edit. The double `scrollTo` is a symptom that the router's "reset scroll on every route change" policy doesn't fit views that mutate in place; distinguishing navigation from re-render in the router would remove the workaround (**likely** to matter as schede grow).

### The window-global shell contract

Views call `window.setViewTitle(...)` to update the header, `impostazioni.js` calls `window.triggerInstall()`, and `app.js` sets `window.__canInstall`. These globals are the actual API between shell and views, but nothing documents or types them. `app.js` also sets a default title from `TITLE_FOR_ROUTE` on route change, then most views immediately call `setViewTitle` again, writing the title twice per navigation. The contract is invisible: a view that forgets `setViewTitle` inherits whatever the previous view left, except for the four routes in `TITLE_FOR_ROUTE`. A small exported `shell` module (`setTitle`, `promptInstall`, `canInstall`) would make the dependency explicit and testable (**confirmed**).

### Dangling exerciseId references after delete

`store.deleteExercise(id)` removes the exercise and its weight logs but does not touch any workout `items` that reference it — `esercizi.js` even acknowledges this in its confirm copy. The render path degrades gracefully (`exName` falls back to `'(esercizio)'`, `getLatestWeight` returns null), so nothing crashes. But the item is now permanently orphaned: it shows a nameless row, and tapping it opens `openExerciseSheet`, which does `const ex = await store.getExercise(...)` and silently `return`s on null — so the row can't be edited or removed through its own sheet. The only escape is the day-level menu. Fix by blocking deletion when referenced, sweeping workout items on delete, or giving the orphaned row a "remove from workout" path (**confirmed**).

### Superset arity is never enforced

A `superset` item is created with exactly two exercises in `addSuperset`, and there's no UI to add or remove sub-exercises, so today supersets always have two. But the model permits any count and `importWorkout` maps `it.exercises` through as-is. An imported file (or a future edit feature) producing a superset with zero or one exercise makes `renderSuperset` draw a "Super serie" label with an empty or single body, and `countExercises`/chart id-collection accept it silently. Latent rather than active, but worth a guard at construction and render time (**likely**).

### No failure surface on writes

Every mutation path — `saveWorkout`, `logWeight`, `deleteWorkout`, `importData`, `importWorkout` — is `await`ed but never wrapped in try/catch at the view layer. `db.put`/`putMany` reject on transaction error (quota exceeded, private-mode restrictions). A rejection propagates to the click handler and is lost as an unhandled promise rejection: the toast and `rerender` never run, and the UI silently shows stale data — the user thinks the save didn't happen, or worse thinks it succeeded because the optimistic in-memory object already carries the change. The router guards render errors but nothing guards the save handlers. Wrapping saves and toasting on failure would make persistence honest about errors (**likely**).

### Import is multi-transaction with no rollback

`importData` clears all three stores, then calls `putMany` separately for exercises, weightLog, and workouts — several independent transactions. If it fails partway (the workouts `putMany` rejects after the clears and the first two puts succeed), the database is left half-populated with no way back, and the user already confirmed the destructive prompt. `importWorkout` similarly interleaves many single `db.put` calls across its loop. This is the highest-stakes operation in the app; a single transaction spanning the stores, or a staged "import into temp then swap," would make it atomic (**likely**).

### Service worker fetch edge cases

The strategy split is right — network-first for HTML/JS/manifest so updates propagate, cache-first for icons. Two gaps in the fetch logic. `isAppCode` returns true for any `url.pathname.endsWith('/')`; combined with the `.catch(() => caches.match('./index.html'))` fallback, a missing app resource offline resolves to the HTML shell, which for a `.js` request is served with the wrong content and fails to execute (**confirmed**). And the cache-first branch has no offline fallback: if an icon isn't cached and the network is down, `fetch(req)` rejects and `respondWith` receives a rejected promise, producing a broken response rather than a graceful miss (**confirmed**).

The `ASSETS` array is the manual source of truth for what's pre-cached, so adding a JS module requires editing the import graph, this array, and bumping `CACHE_VERSION` — an easy step to forget, which silently drops the new module from the offline cache (**confirmed**, low severity).

### What's clean and worth keeping

`logWeight`'s same-day upsert (find the entry for the date, update in place) prevents duplicate daily entries. The single-workout `exportWorkout`/`importWorkout` pair correctly walks supersets vs singles when collecting `exerciseId`s, remaps ids on import, dedups exercises by name, and resets `done`/`pushNext` flags. The picker's `MutationObserver` resolving the promise with `null` on any close path (✕, Escape, backdrop) cleanly handles dismissal-without-choice, and `chart.js` guards the single-point (`xMin === xMax`) and empty-series cases.

### Test coverage

No tests exist (no runner in the tree, no spec files). The highest-value targets are pure and easy to isolate: `parseRestSeconds` (in `scheda.js`), `logWeight` upsert semantics, `importWorkout` id-remapping and exercise dedup, `exerciseIdsInWorkout` superset traversal, and `chart.js` scale math. Not tested: any of these. The merge-import path in particular is complex enough that a regression would be silent and data-losing.
